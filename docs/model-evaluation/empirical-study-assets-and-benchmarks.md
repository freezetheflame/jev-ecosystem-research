# Empirical study：已有资产与公开任务复用

整理日期：2026-10-15。状态：本地文件盘点、官方材料核对及待审核候选整理；没有新增模型调用、没有运行 Agent、没有修改历史标签。RQ 和正式实验划分尚未冻结。

## 1. 当前建议

**主实验复用公开的任务、环境、工具及评测器；我们实现 Jev 接入、记录和受控对照。自建样本仅在公开任务缺少必要机制对照时补充。**

首选核查 AgentDojo 的原始可执行环境。InjecAgent 作为工具返回注入的独立补充候选。若研究范围扩展到直接有害请求或记忆投毒，再分别考虑 AgentHarm、ASB。这是一套适配优先级，不是已经完成安装和兼容性验证的选型。

此前建议“20–30 个场景”应理解为**从已有任务中选取并审核**，并不要求我们从零创作。现有 60 场景鲁棒性草案也不必全部自建：可在审核后的公开任务上派生必要变体；原协议需在实施前相应更新。

## 3. 公开基准应承担什么角色

| 基准 | 官方提供的材料／关注问题 | 本研究建议用途 | 适配边界 |
|---|---|---|---|
| **AgentDojo** | 任务环境、工具运行时、用户任务、注入目标及任务评测方法；支持组合 Agent pipeline 与防御组件 | **闭环主实验首选**；在同一环境中比较无 Jev、门控、上下文筛选及组合配置，另记总成本 | 固定代码和 benchmark 版本；结果判定只覆盖已定义目标，不是全部安全属性；需逐任务核查判分 |
| **InjecAgent** | 工具返回中的间接提示注入案例与 Agent 评测代码；含直接伤害和数据窃取设置 | 工具观察／动作选择的独立补充与迁移测试 | 其 ASR、有效输出分母及数据窃取阶段需按原协议解释；不可直接等同 AgentDojo 的完整任务效用 |
| **AgentHarm** | 显式恶意用户任务及多步工具使用评价 | 若保留“用户本身有害请求”方向，作为单独实验 | 用户意图与间接注入不同；本地 TS-Bench 派生片段不等于运行了 AgentHarm |
| **ASB** | 多场景 Agent 框架及直接／观察注入、记忆投毒、PoT 后门设置 | 后续扩展记忆与更多攻击面 | 不同攻击权限分开；本地 ASB 派生子集有工具名称捷径线索，不能据此断言上游所有设置都存在同一问题 |
| **已有静态集** | MSB、MCPTox 文本、NotInject、ATBench 等本地记录 | 离线诊断、误报分析与回归 | 本地使用方式是静态评判；即使原基准支持运行 Agent，也不自动继承其闭环证据 |

以上在线核查依据：

- AgentDojo [官方仓库](https://github.com/ethz-spylab/agentdojo)、[任务与环境文档](https://agentdojo.spylab.ai/concepts/task_suite_and_tasks/)、[Agent pipeline 与防御文档](https://agentdojo.spylab.ai/concepts/agent_pipeline/)。任务中有 `utility`、攻击目标中有 `security` 方法；必须在固定版本中验证返回值含义，不能仅凭函数名猜测安全指标方向。
- InjecAgent [官方仓库](https://github.com/uiuc-kang-lab/InjecAgent)。
- AgentHarm [原论文 v3](https://arxiv.org/abs/2410.09024v3)。本轮未成功核验其运行仓库入口，不标记为本地已接入。
- ASB [官方仓库](https://github.com/agiresearch/ASB)。

本轮是官方文档／README 级核查，不是四个框架的完整源码审计或安装验收，也不是穷尽式最新基准综述。最终选型前应保存具体 commit、依赖、许可及任务版本。本地 AgentDojo raw 目录只有 31 个文件，未包含 `environment.yaml`，因此这份目录本身不足以证明完整环境已经就绪。

## 4. 哪些工作必须自己做

| 层次 | 尽量复用 | 需要我们完成 |
|---|---|---|
| 任务与工具 | 官方用户任务、初始状态、工具实现、注入位置 | 检查适配性，冻结版本和任务清单 |
| Agent | 官方 pipeline 与工具循环 | 接入选定主模型，固定系统提示和执行预算 |
| Jev 组件 | 现有客户端与日志思路 | 明确可见输入、来源边界、门控操作与上下文筛选范围 |
| 判分 | 原任务效用与攻击目标评测器 | 审核判分范围；补记录合法任务受阻、恢复、复核、成本与延迟 |
| 机制对照 | 原始任务及现成攻击 | 仅在必要时派生等价改写、伪授权／真授权等最小变体，逐例审查标签是否应变 |

自定义变体属于**派生诊断集**。应保留原始版本并单独报告，不把改写后的任务称为原 benchmark 官方成绩。真实授权变化可能要求改变用户任务和效用判定，不能只改一行文本便假定旧评测器仍正确。

建议用原始任务回答“是否有效”，用有限的受控变体回答“为什么失效”。两部分共享溯源，但不混合分母。

## 5. 首批审计队列：已有任务，不是新造样本

[review-candidates.json](../../data/empirical-study-preparation/2026-10-15/review-candidates.json) 已列出 24 个本地 AgentDojo 用户任务候选：四个 suite 各 6 个。按 `SHA256("audit-20261015:" + uid)` 排序选取，不读取模型预测，也不只挑 Jev 失败样本；不是上游全集的随机代表样本。

每项保留原 UID、suite、任务类、局部 patch 版本、原始定义文件及哈希。所有记录均为 `pending_manual_audit`，尚未匹配有效注入任务、尚未验证可执行环境，也没有我们新增的动作级 gold。**24 个候选是开发审计入口，不是已完成的 24 个攻击场景。**

逐项审核要填写：

1. 用户任务全文、任务族、原始环境与判分函数。
2. 攻击者目标、可修改的位置、实际载荷、与用户任务的有效匹配。
3. Jev 调用时可见的历史与动作；不含未来结果或攻击 gold。
4. 任务成功与攻击成功各自怎么判断，是否存在评测器遗漏。
5. 若需要动作级标签，独立记录当前动作的授权依据；不能从 episode 的成功标志机械推导。
6. 适合门控、上下文筛选还是两者；若任务没有足够上下文可筛，标为不适用。
7. 保留／排除／待确认及理由。问题样本不能因为模型表现差而被排除。

先从每个 suite 各审核一个，核对任务、注入与判分的对应关系，再扩展到 24 个。使用过的开发任务族及其变体应与正式确认集隔离；不把同一任务的不同攻击变体拆到调参与测试两侧。

## 6. 与当前 RQ 和成本研究的关系

| 问题 | 已有基础 | 接下来需要补的证据 |
|---|---|---|
| 安全效果与适用角色 | 静态预测、动作问句、模拟门控 | 原始可执行任务中的安全与效用结果 |
| 鲁棒性与失败机制 | JevOut 方法经验、来源对照协议 | 合法的攻击权限、可审核变体、重复及独立验证 |
| 接入与组合策略 | 客户端、门控操作和 pipeline 接口候选 | 固定事实和可见信息的对照；组件改变轨迹后重新运行 |
| 成本与效率 | 旧有效 Jev 记录有 usage/latency，部分新记录有请求或配置哈希 | 主 Agent、Jev、实际复核与恢复的总账；任务端到端时间；缓存命中及真实远端调用区分 |

本轮确认旧 Jev 13,173 条有效结果均有 `latency_ms` 和非空 `usage`；但这些字段并不自动提供完整请求、价格版本或闭环费用。模拟器日志中的调用耗时也不能未经缓存口径核查就当作真实在线推理时延。成本结论仍需与安全、任务完成率一起验证。

## 7. 当前可推进与暂缓项

可以推进：原任务/评测器审计、固定版本可获取性检查、无模型调用的环境与日志流程验证。

暂缓：根据旧结果选最终阈值、扩写完整自建 benchmark、大规模多模型扫描、提前写正式贡献或新颖性结论。

下一步的具体交付应是**四个完整任务审计卡片及其原始判分依据**，再决定哪些候选进入适配。这样即使 RQ 调整，也能复用现有工作。
