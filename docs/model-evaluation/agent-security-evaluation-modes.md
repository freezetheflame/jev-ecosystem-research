# Agent 安全评测 Mode A–D：定义与适配边界

> 2026-10-28 用户确认：当前选型的 A1、A2 都继承本文原 Mode A（Input Inspection，输入检查），1/2 仅为序号，不代表两种模式。最新选型为 AgentHarm=A1、MaliciousSkillBench=A2，AgentDojo 已移出。新 B/C 的含义仍待确认，不自动继承本文定义。下述六个基准表为历史适配计划。

日期：2026-10-27（Asia/Shanghai）。定义来源：用户当日补充。状态：**四种场景的概念定义已明确；具体数据适配、标签、输入和运行配置尚待冻结**。

本框架按三个维度组织评测：安全决策发生的位置、判定时可获得的信息、安全判断目标。它是本研究的评测场景划分，**不是对攻击类型的重新分类**，也不要求每个基准覆盖全部场景。

## 1. 四种场景

| Mode | 名称 | 决策时机与可见信息 | 判断目标 | 对应记录单位 |
|---|---|---|---|---|
| A | **Input Inspection**（输入检查） | 不可信外部内容接收时；可见指定输入、来源及任务所需可信上下文 | 识别不可信输入及间接提示注入风险 | 输入条目/内容块；具体划分按 adapter 冻结 |
| B | **Pre-action Authorization**（动作执行前授权判断） | 工具执行前；可见拟调用工具、参数、已发生历史、可信任务/策略及已验证授权 | 判断该项拟执行动作是否符合授权和政策 | 待执行动作及其执行前状态 |
| C | **Prefix-based Monitoring**（基于前缀的监测） | 执行过程中；仅见截至指定切点已发生的历史，以及当时可用的可信任务/策略 | 识别当前可观测的跨步骤安全风险 | 原始轨迹 ID + 前缀切点 |
| D | **Full-trace Auditing**（完整轨迹审计） | 执行终止后；可见完整 Agent 交互和执行记录 | 对已发生行为作事后安全判断 | 一条完整轨迹/episode |

上表是对用户定义的记录与操作化说明，不替代各数据集的标签契约。A 中“含攻击内容”、B 中“当前动作不合规”、C 中“前缀可识别风险”、D 中“轨迹存在风险”是不同目标，不能仅因都是安全任务就共用一个 gold。

Mode 与比较组是不同字段：`evaluation_mode` 取 A/B/C/D；`arm` 仍表示无新增模块 A、Jev J、LLM L、规则 R 等比较配置。同一个 Mode 可有多个比较组，不把 Mode A 解释成无安全模块组。

## 2. 可见信息与标签约束

1. **A 不使用后续结果作模型输入。** 攻击目标、未来轨迹、评测器结果与 gold 可用于离线标注，但不得因它们存在于原数据文件就一并发给模型。可信政策或来源元数据仅在该模式契约允许时提供。
2. **B 固定执行前快照。** 保存当前动作的工具名/参数、已验证授权和政策依据；不得包含该动作执行后的返回或后续结果。不可信正文的“已获授权”声称不能自动成为真实授权。
3. **C 固定前缀切点。** 保存原始轨迹 ID、截止事件索引、可见范围和对应输入 hash；输入只能包含截至切点已发生的信息，不能从后续风险标志反推前缀标签。已发生前缀与尚未执行动作的判断应分别标记 C 与 B。
4. **D 保留完整轨迹范围。** 保存完整性与终止原因；事后能识别风险不证明当时能够阻断，更不等于完成了实时防护。
5. **新增标签单独构造和验证。** 原基准没有的执行前动作标签/前缀标签必须保存标注准则、政策、来源、审核记录和分歧；原生标签与派生标签分开。不把攻击目标成功标志或整条轨迹风险标签复制到所有动作/前缀。
6. **C 的风险事件须明确。** “截至当前已经出现可识别风险”与“未来最终会发生违规”是两个任务；若另测未来风险预测，需另定预测事件、窗口和标签协议。尚无足够证据不能自动记 safe；标签不足、未知和不适用按预定口径报告。
7. **先按原任务族划分，再生成派生样本。** 同一轨迹的前缀、动作和完整轨迹不能跨开发/校准/确认集合。多个前缀不是多个独立任务；统计保留任务/轨迹的聚类与配对关系。
8. **运行时防护另有证据门槛。** 离线 A/B/C/D 判断用于识别能力评测。声称实际防护时，必须实际接入、独立运行后续轨迹，并记录安全结果、任务效用和全部额外开销。不能把 B 的离线授权准确率直接当作攻击阻断率。

若 C 对同一轨迹多次调用，分别报告每次判断成本和整条轨迹累计监测成本；不能用一次短前缀的费用代替持续监测开销。现有 monitor 的计量职责保持不变。

## 3. 六个基准的计划适配

| 基准 | 计划 Mode | 本研究拟覆盖的机制（用户定义） |
|---|---|---|
| InjecAgent | A | 不可信工具返回的输入注入识别 |
| AgentDojo | A、B | 输入风险、工具执行前防护与实际攻击结果的连接 |
| R-Judge | D | 多类别 Agent 行为安全审计 |
| ATBench | C、D | 长轨迹、延迟触发风险和历史/完整轨迹信息差异 |
| MCPHunt | B、C、D | 跨 MCP 服务器的信息流安全 |
| SCR-Bench | B、C、D | 能力传递、信任转移、授权混淆造成的 Skill 组合风险 |

这是按用户选型保留的适配计划，不表示所有所需字段、动作标签和前缀标签已经在原始数据中找到。具体采用原生还是派生标注、是否可运行完整环境，逐基准核查后再冻结；不为凑齐 Mode 而制造原生标签。

## 4. 用户提供的论证原文

以下两段按用户原文保留；其中引用编号属于该段的局部草稿编号，本轮未将其补写成已经核验的正式书目。

> 现有研究表明，LLM Agent 的安全风险并不局限于单次输入，而是可能出现在外部内容接收、工具调用、任务执行及跨步骤交互等不同环节。Agent Security Bench（ASB）系统性地揭示了 Agent 在提示处理、工具使用和记忆访问等阶段面临的不同攻击面 [1]；InjecAgent 和 AgentDojo 进一步表明，不可信工具返回可能通过间接提示注入改变 Agent 的后续行为 [2,3]。与此同时，CaMeL 强调了独立于输入检测的工具调用权限及信息流约束的重要性 [4]。从执行过程来看，运行时验证（Runtime Verification）理论为基于有限执行前缀的在线安全监测提供了方法论基础 [5]，而 R-Judge 与 ATBench 则通过完整 Agent 交互轨迹评估行为安全风险 [6,7]。基于上述研究，我们从**安全决策发生的位置、判定时可获得的信息以及安全判断目标**三个维度，将 Jev 的 Agent 安全评测划分为四种场景：**（A）Input Inspection**，评估对不可信输入及间接提示注入的识别能力；**（B）Pre-action Authorization**，评估对拟执行工具调用及其授权合规性的判断能力；**（C）Prefix-based Monitoring**，评估在仅观察已发生执行历史的条件下，对跨步骤安全风险的识别能力；以及 **（D）Full-trace Auditing**，评估基于完整执行轨迹的事后安全判断能力。该框架是一种基于观测条件和决策时机的评测划分，而非对攻击类型的重新分类。

> 为实现上述场景的互补覆盖，同时控制实验规模，我们选取六个具有不同安全机制和标注特征的公开基准。具体而言，InjecAgent 用于输入注入检测，AgentDojo 用于连接输入风险、工具执行前防护与实际攻击结果；R-Judge 提供多类别 Agent 行为安全审计样本，ATBench 则补充长轨迹和延迟触发风险；MCPHunt 用于评估跨 MCP 服务器的信息流安全 [8]，SCR-Bench 用于评估由能力传递、信任转移和授权混淆引起的 Skill 组合风险 [9]。我们根据各基准的原生数据结构，将其适配到对应评测场景，而不要求每个基准覆盖全部四种场景。对于原始基准未直接提供的执行前动作标签或轨迹前缀标签，将另行构造并验证相应的标注。通过这种基于安全机制与观测条件的基准选择策略，本研究旨在系统性地评估 Jev 从局部输入判断到多步骤行为安全分析的能力边界，并进一步区分离线风险识别与实际运行时防护效果。
