# RAG 的安全定论，以及 Jev 能替换其中的哪些 LLM 节点

整理自 2026-10-02 的调研。两个问题分开回答：RAG 到底算不算安全方案；Jev 能不能顶掉 RAG 流水线里的 LLM。

---

## 一、RAG 有安全的说法吗？有，而且 2026 年才刚标准化

**OWASP LLM Top 10 在 2026 版把「向量与嵌入弱点」单列成一条**（不同来源编号有出入，大致落在 LLM07–LLM09）。2025 版里没有这一条。它点名的正是 RAG 专属攻击：

- 嵌入反演（从向量还原原文）
- 语义后门（污染语料使特定查询命中攻击者内容）
- 检索绕过
- 跨租户数据泄露

这类漏洞在传统 AppSec 工具里**没有对应物**，扫描器扫不出来。

### "RAG 更安全"这句话，对一半错一半

**对的一半**：RAG 把知识从权重里挪到了检索层，于是**权限可以在检索层强制**（"检索前鉴权"）。这是微调做不到的——权重里的数据理论上都能被提示套出来，而检索层可以按用户身份过滤。

**错的一半**：RAG 没有缩小攻击面，它**新增了一条**。原本攻击只能走用户输入一个入口，现在**语料库本身成了注入载体**——一份被投毒的内部 PDF，就能把模型变成"混淆代理人"。而且幻觉没有消失，只是**失败点从模型推理转移到了检索质量**：检索错了，你会得到一个"带参考文献的自信谎言"。

### 定论

> **RAG 用一类可控的工程风险，换掉了一类不可控的模型风险。它不是安全方案，它是把安全问题变成了架构问题。**

治理要点三条：

1. 身份必须透传到检索层——不能用全局服务账号绕过 SharePoint / Drive 权限
2. 显式设计拒答路径（检索不到就拒绝，不要让模型硬编）
3. 每条回答都能溯源到具体文档

## 二、Jev 能替换 RAG 里的 LLM 吗？能，但只在决策节点

关键认知：**"RAG 中的 LLM"不是一个角色，是两类**——一类在做判断，一类在写文本。Jev 只能接前者。

判断依据极其简单：**看这个节点的输出 schema**。

- 输出是 `boolean` / `enum` / 0–1 概率 / 小范围整数 → 决策节点，**Jev 可换**
- 输出是自由文本（摘要、回答、解释） → **接不了**，Jev 根本不生成文本

### 能换的三处，和它们的真实收益

| 节点 | 换成 Jev 后 | 为什么能换 |
|---|---|---|
| **查询路由** | 判断这问题要不要检索、要不要强模型，不再用强模型做判断 | 输出是 enum（寒暄 / 检索 / 多步分析） |
| **重排过滤** | 60 个候选 chunk 打分后只留 top 5–10 进上下文 | 输出是 0–1 相关性概率，概率本身就是分数 |
| **引用核查** | 判断被引段落是否真的支撑该句主张 | 输出是 boolean |

收益是三重的：成本、延迟、以及**接地质量**——垃圾 chunk 不进上下文，就少一个带偏最终答案的机会。

数字：Jev 定价 \$0.042/百万输入 token、输出免费，70–500 ms。一次查询过滤 60 个 chunk（约 18k token）≈ **\$0.76/千次查询**。厂商演示 BM25 top-1 从 21% 提到 54%（厂商自测，可信度中等，但方向与其他来源一致）。

### 两处绝对不能换，一个只能当辅助

**权限校验和输出消毒必须在代码层。** 这不是模型能力问题，是 OWASP 的明文立场：隐藏上下文 / 策略文本不能作为授权的唯一依据。

**注入筛查只能当辅助层，不能当闸门。** 用 Jev 扫检索结果里的越权指令，本质是"用 AI 挡 AI"，而且它**多给攻击者增加了一个可操纵的失效点**——语义后门和嵌入投毒干的就是让筛查器把恶意文档判成 safe。真正该做的是纵深防御：检索前鉴权是主控制，Jev 筛查只是其中一层。

### 一个结构性收益（不是营销）

Jev 不产出文本，所以路由 / 分类节点**不可能**成为 XSS 或代码注入的源头。这一部分是实打实消掉的。

## 三、硬警告：密封集坍塌对 RAG 场景尤其致命

见 `01-jev-open-ecosystem.md` §4.3。**公开题 86%、密封题 37% 是普遍现象，原版 Jev 自己就是 86.6% → 36.7%**（随机基线 29.3%）。而 RAG 恰恰是语料持续漂移的场景。推论：

1. **阈值不能"设一次用一年"。** 在自己语料上标定的 0.7 阈值，换一批文档、换一个业务域就可能失效。必须就地标定 + 定期重标。
2. **概率好 ≠ 判定对。** 校准分高只说明自信度和正确率一致，不说明判得准。
3. **chunk 顺序会毒化判断。** 实测有模型把选项顺序反转后准确率从 72% 掉到 21%。让每个 chunk 独立打分、固定顺序，别让 chunk 之间互相影响。

两个硬限制：state + 所有问题合计 **32k 上限**（长文档和多轮 agent state 会撞墙）；Choice 最多 **255 个选项**，开放分类得穷举。

---

## 四、落地建议

**先切重排过滤**——ROI 最高，判错了只是质量下降，不是安全事故。

**别先切注入筛查**——那是判错就要出事的节点。

中间地带（0.4–0.7）送人审或交给大模型兜底，别硬设单点阈值。

数据不能出境就别用 API，用开源复现自建（例如基于 Qwen3.5-9B 微调、Apache 2.0 的那一类）。

> **一句话总结：Jev 换掉的是 RAG 里的"判断"，不是"知识合成"。它是接在 LLM 前面的一层质检，不是替代品。**
