Abstract.
 

Agentic software connects language models to tools that modify files and interact with external services. Developers use model-based security checks to screen external content and user requests before agents act. System One models answer developer-defined questions with probabilities over predefined answers such as safe or unsafe, but classification accuracy alone does not establish whether these probabilities support reliable automation. We evaluate Jev, Laya, Decider, and Bespoke Nimble against specialized classifiers and language-model judges across prompt-injection detection, interaction-risk judgment, and harmful-request screening, examining decision accuracy, calibration, and selective automation. (1) High overall accuracy and low average calibration error can conceal attacks classified as safe with high confidence within particular groups. Developers should test candidate models on the intended security task and examine errors within relevant attack groups. (2) Policies selected under strict miss limits allow few test inputs automatically, and choosing allow and block thresholds separately increases automation mainly through additional blocks. Developers should verify limits on missed unsafe inputs and blocked benign inputs on independent data, and report the allowed and blocked fractions separately. (3) Comparing predictions on the same inputs shows that a language-model judge can detect unsafe inputs missed by a System One model, but can also repeat the System One model’s confident mistakes and falsely flag benign inputs. Developers should test which missed unsafe inputs their review rule forwards, then measure the review model’s misses and benign false alarms on those inputs.
 


Keywords: AI agents, probabilistic decisions, calibration, security evaluation



1. Introduction



Agentic software combines language models with tools that inspect and change external state. Agents retrieve documents and use services to complete user tasks, or navigate repositories, edit code, and execute tests (Debenedetti et al., 2024; Yang et al., 2024). Unlike a standalone text response, an agent’s interpretation of an input can affect files, accounts, or subsequent tool calls. Developers therefore need to decide which information the agent may trust and which operations it may perform. Runtime enforcement systems such as AgentSpec make these constraints explicit in software (Wang et al., 2026a).



Tool access also creates security challenges. Instructions embedded in external content can redirect an agent, and the requested task itself may involve harmful conduct (Greshake et al., 2023; Andriushchenko et al., 2025). For example, a document retrieved for summarization may contain an instruction to send private information to an external address. A security check needs to assess that instruction in relation to the user’s task before the agent acts on it. Model-based judges can screen such content, user requests, or interaction records. Missing an attack can expose the agent to unauthorized behavior, while rejecting harmless content can interrupt legitimate work.



System One models (TypeSafe, ) are designed to make fast, structured decisions. They take an input and a developer-defined question, then assign probabilities to predefined answers such as safe or unsafe instead of generating a free-form response. Jev, Laya, Decider, and Bespoke Nimble offer implementations of this interface (TypeSafe, ; convaiinnovations, ; Mapika, ; Bespoke Labs and Sathiamoorthy, 2026). Figure 1 shows this process for three security checks. The application gives the decision component both the input and a task-specific question, such as whether a retrieved page contains a prompt injection. The model returns an unsafe probability. A security policy converts that probability into an action: allow the page to reach the agent, block it, or escalate it for review. For example, the policy can allow low-scoring pages, block high-scoring pages, and send the remaining pages to a second judge, another model that reassesses the input. Similar checks can screen a user request before task execution or assess risks in an interaction record. The policy shown in the figure remains fixed when evaluated on new inputs.


Figure 1. Security tasks and probabilistic decisions.Three input types pose different questions: prompt injection in external content, risk in an interaction record, and harm in a user request. The selected input and question enter a decision component, which returns an unsafe probability for a policy to map into allow, escalate, or block.



Decision automation means handling an input without further review, either by allowing or blocking it. We assess its usefulness on labeled data by measuring the fractions of unsafe inputs allowed and benign inputs blocked. We use error limits as acceptance criteria for these observed rates. For example, a policy meets a 1% miss limit on 100 unsafe evaluation inputs if it allows at most one of them. These limits express the application’s tolerance for missed threats and interrupted legitimate work. The policy makes decisions from model probabilities, and labels are used to check its errors during evaluation. Sending every input for review meets both limits but provides no automation.



Using probability cutoffs also requires understanding calibration, the agreement between reported probabilities and observed outcomes (Guo et al., 2017). If inputs assigned an unsafe probability near 0.8 are well calibrated, about 80% should be unsafe. Prior work reports attacks classified as safe with high confidence and errors repeated by multiple judges (Biswas, 2026; Rao and Callison-Burch, 2026). Developers therefore need to validate labels, probabilities, and the actions chosen by the policy together (Amershi et al., 2019; Breck et al., 2017). Strong classification accuracy alone does not establish how much work a policy can automate while meeting both error limits.



We investigate the following question: When can developers use System One model judgments and probabilities to automate security checks in agentic software? We evaluate judgments and policies offline on WAInjectBench, R-Judge, and AgentHarm using their original labels. We compare System One models with language-model judges and task-specific classifiers, and Decider and Nimble with their base models. Three research questions organize the evaluation.



RQ1: How accurately do models make security decisions?



We compare missed unsafe inputs and benign false alarms across tasks and attack groups. The observed differences show why developers should select models for the intended security check and examine attack groups that overall rankings can obscure.




RQ2: How well calibrated are the unsafe probabilities?



We assess the unsafe probabilities returned by each model and test recalibration fitted on development data. Average calibration can conceal confident misses, so developers should also check the observed unsafe fraction among inputs a policy would allow.




RQ3: How many inputs can a fixed policy process automatically within the error limits?



We compare fixed policies under limits on missed unsafe inputs and blocked benign inputs, and assess language-model judges as potential reviewers. Separately selected cutoffs can increase automation through additional blocks, yet some policies exceed their limits on test data. Developers should therefore verify both policy error rates on independent inputs and assess which errors a second judge corrects or introduces among the cases selected for review.



The study makes three contributions:


• 


An empirical study connecting decision errors, probability calibration, and automatic security checks across System One models, specialized classifiers, and language-model judges.


• 


Evidence that aggregate performance and probability quality do not consistently establish how many inputs a software policy can process within fixed error limits.


• 


Engineering implications for validating security checks, choosing allow and block thresholds, and selecting review judges, supported by a public replication artifact.







2. Background and Related Work



2.1. System One Models



The name System One evokes fast, intuitive System 1 thinking (TypeSafe, ). Answers are typed because developers specify their format and allowed values, such as a Boolean, a category, or an ordered score. For a prompt-injection check, developers supply a tool response and ask whether it is unsafe. The model assigns probabilities to safe and unsafe without writing an explanation.



Jev reports answer probabilities (TypeSafe, ), Laya uses encoder decision heads (convaiinnovations, ), and Decider and Nimble score candidate answers with language-model backbones (Mapika, ; Bespoke Labs and Sathiamoorthy, 2026). Changing the question and allowed answers lets developers reuse the same typed interface across security checks (TypeSafe, ).




2.2. Agent Security Evaluation



Indirect prompt injection places attacker instructions in retrieved data and can redirect a language-model application’s behavior (Greshake et al., 2023). Existing benchmarks evaluate several security judgments relevant to agents: R-Judge labels interaction risk (Yuan et al., 2024), AgentHarm supplies harmful and benign requests (Andriushchenko et al., 2025), and WAInjectBench evaluates web-agent injection detection (Liu et al., 2026).



Detector evaluations document high-confidence false negatives under changes in attack distribution (Biswas, 2026) and false positives on difficult benign inputs (Shire and Kim, 2026). For typed decision models, Sun et al. show that outputs can follow an answer option’s name rather than its attached definition, even when they satisfy the required format (Sun et al., 2026).



AgentDojo evaluates security and utility in an executable agent environment (Debenedetti et al., 2024). CaMeL constrains information flow (Debenedetti et al., 2026), AgentSpec enforces developer-defined runtime constraints (Wang et al., 2026a), and ProbGuard predicts execution safety from agent states (Wang et al., 2026b).




2.3. Calibration and Selective Prediction



Calibration measures whether predicted probabilities match observed outcome frequencies. Temperature scaling fits a probability transformation intended to improve that match (Guo et al., 2017), while changes in the input distribution can undermine it (Ovadia et al., 2019). Selective classification and SelectiveNet defer uncertain predictions, trading the fraction accepted automatically against their error rate (Geifman and El-Yaniv, 2017; Geifman and El-Yaniv, 2019). Conformal risk control provides guarantees on expected loss when its monotonicity and sampling assumptions hold (Angelopoulos et al., 2024).



For alignment-failure detection, Guo et al. show that calibration averaged across benchmarks can hide mismatches between Jev’s probabilities and observed failure rates within individual benchmarks (Guo et al., 2026). Confidence-based escalation sends uncertain inputs to another model for a further judgment. Li et al. study this approach for preference and factuality judging (Li et al., 2026), while Rao and Callison-Burch show how shared high-confidence errors limit its benefit (Rao and Callison-Burch, 2026). We examine probabilities and fixed decision rules across security tasks, and compare models’ errors to assess their potential to review one another’s decisions.





3. Study Design



The study checks whether models return correct labels (RQ1), assign probabilities that reflect observed unsafe frequencies (RQ2), and support automatic decisions within specified error limits (RQ3).
Figure 2 shows how predictions on the same benchmark inputs support the three analyses. Benchmark labels are used for evaluation and excluded from model inputs.



3.1. Models and Baselines



We compare System One models with general-purpose language-model judges and task-specific classifiers. Parent controls use the original base models to measure changes after adaptation for typed decisions. Table 1 defines twelve primary configurations and their applicable tasks.



We evaluate ProtectAI, PIGuard, and Prompt Guard 2 only on injection detection (Protect AI, 2024; Li et al., 2025; Meta, ). WildGuard evaluates AgentHarm request harmfulness using its released prompt template (Han et al., 2024). For Decider and Nimble, we evaluate the original parent weights with the same candidate-scoring procedure at temperature one (Mapika, ; Bespoke Labs and Sathiamoorthy, 2026). Scoring temperature controls how concentrated the candidate probabilities are. The adapted models retain their released temperatures, so comparisons can reflect both weight changes and probability scaling.

3.2. Benchmarks and Data Partitions



The study uses three public benchmarks with their original annotations. R-Judge supplies complete interaction records with binary risk labels, while AgentHarm divides requests into harmful and benign sets. WAInjectBench annotates attack-derived text segments as containing explicit instructions (EI), which directly tell an agent what to do, or lacking them (no-EI) (Liu et al., 2026). Both groups retain their released unsafe labels, including attack-derived segments without direct commands. Each probability is evaluated against the unsafe event defined by its benchmark. Decision inputs exclude labels, risk explanations, hidden attacker goals, class-revealing filenames, and future outcomes.



The partitions in Table 2 separate calibration and threshold selection from testing. Inputs used during pipeline development form the development set for fitting recalibration. For R-Judge and WAInjectBench, a fixed stratified split assigns the remaining inputs to selection, confirmation, and test. Identical inputs are grouped before splitting and represented once, preventing duplicates from crossing partitions. Selection inputs determine thresholds that act as probability cutoffs for allowing or blocking inputs. Confirmation and test inputs assess those settings without retuning. We call the non-test partitions source data. AgentHarm retains its official split, using eight validation task groups for development and 44 groups for test. Without separate selection and confirmation sets, it supports classification and calibration evaluation but is excluded from the policy experiment.

3.3. Input and Output Standardization



For each task, adapters present the same complete benchmark input and safe/unsafe label definitions through each model’s interface. We extract the predicted label and any available unsafe probability from each response. Classification uses valid labels, while probability analyses use a label and score from the same response (Section 5). We count the complete formatted input with each model’s tokenizer and do not truncate benchmark records. The English Laya checkpoint uses a 2,048-token budget. Nimble and its base-model control use their scorer’s accepted budget of 262,143 tokens, with 2,155 tokens as the longest formatted input in this study.



Figure 3 illustrates a rule that allows inputs below 10.5% unsafe probability, blocks those above 89.5%, and sends the rest for review. Laya correctly labels both inputs, but the injection’s 52.87% probability requires review under this rule, whereas the benign notice’s 10.18% leads to an allowance. A correct label therefore need not lead to an automatic decision. Section 6 explains how we select and evaluate these rules.

3.4. Statistical Analysis



We estimate 95% confidence intervals (CI) from 2,000 cluster-bootstrap resamples that keep related inputs together. Paired comparisons use the same resampled inputs for both models. Groups contain identical R-Judge inputs, WAInjectBench inputs from the same released source family, or AgentHarm variants of the same original task across labels and augmentations. We also check sensitivity to grouping R-Judge inputs by source family.



For paired differences in false-negative and false-positive rates, cluster-level sign-randomization tests reverse the direction of each cluster’s difference under the null hypothesis that model identities are exchangeable. Holm correction accounts for multiple comparisons within each benchmark and error metric. McNemar’s test serves as a secondary check under the assumption of independent inputs.





4. RQ1: Security Decision Quality



RQ1 asks how accurately models identify unsafe inputs. We compare missed unsafe inputs and falsely flagged benign inputs, then examine how these errors differ by task, attack group, and model adaptation.



4.1. Metrics and Comparison Populations



We treat unsafe inputs as positive and report Macro-F1, precision, recall, the false-negative rate FNR=FN/(TP+FN)\operatorname{FNR}=\operatorname{FN}/(\operatorname{TP}+\operatorname{FN}), and the false-positive rate FPR=FP/(TN+FP)\operatorname{FPR}=\operatorname{FP}/(\operatorname{TN}+\operatorname{FP}) on valid decisions. Here TP, TN, FP, and FN are true-positive, true-negative, false-positive, and false-negative counts. Area under the receiver operating characteristic curve (AUROC) and average precision (AP) measure score ranking, with AP summarizing the precision–recall curve. Table counts NN denote the inputs in each comparison. Every applicable model returns a valid label on every test input, enabling same-input comparisons within each task.




4.2. Classification Results and Error Patterns



No primary configuration has the highest Macro-F1 on all three tasks, and similar scores can accompany different miss and false-alarm rates. Tables 3 through 5 rank configurations by Macro-F1 point estimates on 1,612 WAInjectBench, 236 R-Judge, and 352 AgentHarm inputs.



Nimble leads the primary WAInjectBench ranking, yet misses 8.1% of attack-derived inputs that directly instruct the agent and 92.3% of those without direct instructions. Jev misses all 130 unsafe no-EI inputs while falsely flagging just one benign input. Before selecting a model for a security check, developers should examine its overall performance and miss rates within relevant attack groups.








   


Finding 1. A model can rank highly overall while missing most attacks in a particular group.






The injection specialists also miss many unsafe inputs. ProtectAI and PIGuard miss over 70% of unsafe WAInjectBench inputs, and Prompt Guard 2 rarely flags any input (FNR 0.989, FPR 0.001). Across the primary comparisons, none of the 16 WAInjectBench FNR/FPR differences is significant after Holm adjustment at 0.05, using twelve source clusters. Jev’s Macro-F1 difference from GPT-4.1 is 0.049 (95% CI [−0.019,0.116][-0.019,0.116]) on their 1,612 shared inputs.



On R-Judge, Jev leads the primary comparison, while Nimble falls from first on WAInjectBench to seventh, flagging 92.8% of benign interactions as unsafe. Qwen3-8B similarly combines few missed unsafe interactions (FNR 0.064) with many false alarms (FPR 0.901).



On AgentHarm, some models miss fewer harmful requests but falsely flag more benign ones. Jev and Nimble reach Macro-F1 scores of 0.840 and 0.831 on 352 test inputs from 44 original task groups. Jev misses 14 of 176 harmful requests and flags 42 of 176 benign requests, while GPT-4.1 misses only one harmful request but flags 85 benign ones. WildGuard detects most harmful requests but flags 71.0% of benign requests. The paired comparison supports Jev’s lower false-alarm rate relative to GPT-4.1: its FPR is lower by 0.244 (95% CI [−0.352,−0.148][-0.352,-0.148], adjusted p=0.0008p=0.0008), while its FNR increase of 0.074 is not significant after adjustment (p=0.50p=0.50).



Decider and Nimble both have higher Macro-F1 than their base-model controls on AgentHarm and lower Macro-F1 on R-Judge. Decider’s differences are +0.351+0.351 on AgentHarm (95% CI [0.276,0.423][0.276,0.423], N=352N=352) and −0.236-0.236 on R-Judge ([−0.314,−0.156][-0.314,-0.156], N=236N=236). On WAInjectBench, confidence intervals for both Macro-F1 differences include zero. Developers should compare an adapted model with its base model on the intended security task before replacing the component.








   


Finding 2. The adapted models have higher Macro-F1 than their base models on some tasks and lower Macro-F1 on others.

4.3. Reasoning Judges



All five reasoning judges have higher R-Judge Macro-F1 point estimates than Jev, with DeepSeek highest.
Tables 6 through 8 compare the five judges with Jev, Nimble, and GPT-4.1 on the same test inputs as the primary rankings.
On R-Judge, DeepSeek’s Macro-F1 exceeds Jev’s by 0.140 (95% CI [0.094,0.187][0.094,0.187]), and GLM-5.3, Kimi, and Qwen3.8 also have positive differences whose paired confidence intervals exclude zero.



On injection detection, GLM-5.3-Flash has the highest Macro-F1 point estimate in the expanded WAInjectBench comparison, followed by Nimble and DeepSeek. For DeepSeek, GLM-5.3, Kimi, and Qwen3.8, the paired Macro-F1 intervals relative to Jev all include zero. DeepSeek’s difference is 0.021 with CI [−0.008,0.057][-0.008,0.057]. Results vary substantially among the twelve source families, which produces wide intervals despite the larger number of individual inputs.



On AgentHarm, Kimi misses none of 176 harmful requests but flags 96 of 176 benign requests as unsafe, compared with Jev’s 14 misses and 42 false alarms. DeepSeek and Qwen3.8 also miss fewer harmful requests but falsely flag more benign ones than Jev. Developers should compare missed harmful requests and benign false alarms against the application’s error limits when choosing a screening model.








   


Finding 3. Fewer missed harmful requests can come with more false alarms on benign requests.

5. RQ2: Probability Calibration



Among inputs assigned an unsafe probability near 0.8, about 80% should be unsafe if the predictions are calibrated. RQ2 examines this agreement across tasks and attack groups, then tests whether recalibration fitted on development data improves test probabilities.



5.1. Probability Scores and Calibration Measures



For System One models, we use the unsafe probabilities returned by their decision interfaces. For general judges, the score is the unsafe answer token’s probability divided by the combined probabilities of the safe and unsafe tokens at the final answer position. GPT-4.1 and Qwen3-8B use separate response configurations for classification and probability analyses, so their predicted labels can differ between these analyses. Recalibration and policy evaluation use the same scoring rule across all partitions. When required labels or scores are missing, we retain the first usable retry regardless of whether its prediction is correct.



For input ii, let pip_{i} be the unsafe probability under evaluation and yiy_{i} its original label, with 1 denoting unsafe and 0 benign. Brier score is the mean of (pi−yi)2(p_{i}-y_{i})^{2}, and negative log likelihood (NLL) is the mean binary log loss, computed after clipping probabilities to [10−7,1−10−7][10^{-7},1-10^{-7}]. Expected calibration error (ECE) compares mean probability with observed unsafe frequency in ten equal-width probability bins. Reliability diagrams plot these two values, so points above the diagonal indicate underestimated unsafe frequencies. Lower Brier, NLL, and ECE values are better. AUROC measures whether unsafe inputs receive higher scores than benign ones, whereas calibration asks whether the numerical probabilities match observed unsafe frequencies. A model can rank inputs well while reporting probabilities that are too extreme, so these measures answer different questions.



We compare the probabilities returned by each configuration, called original scores, with scores recalibrated by temperature scaling (Guo et al., 2017). After clipping, we divide the score’s log odds by a temperature TT and convert back to a probability. We fit T∈[0.05,20]T\in[0.05,20] by minimizing NLL on development inputs from both classes. Original and recalibrated scores are evaluated on the same inputs, with model weights unchanged.

6. RQ3: Automation within Error Limits



RQ3 examines how many inputs a policy can process without review while limiting how often it allows unsafe inputs or blocks benign ones. These limits, called error budgets, are checked using benchmark labels on confirmation and test inputs after thresholds are fixed. We also compare model errors to assess potential reviewers.



6.1. Decision Policy and Error Measures



The policy compares unsafe probability pip_{i} with an allow threshold τL\tau_{L} and a block threshold τH\tau_{H}:




(1)

Decision={𝖺𝗅𝗅𝗈𝗐,pi<τL,𝖻𝗅𝗈𝖼𝗄,pi>τH,𝖾𝗌𝖼𝖺𝗅𝖺𝗍𝖾,pi∈[τL,τH].\text{Decision}=\begin{cases}\mathsf{allow},&p_{i}<\tau_{L},\\
\mathsf{block},&p_{i}>\tau_{H},\\
\mathsf{escalate},&p_{i}\in[\tau_{L},\tau_{H}].\end{cases}



Inputs exactly at either threshold, or without usable scores, also escalate for review. Automatic coverage is the fraction allowed or blocked, while allow coverage counts only allowances. Both use all partition inputs as the denominator. We report them separately because high coverage can result from blocking many inputs while allowing few to proceed. The unsafe-miss rate Missauto\operatorname{Miss}_{\rm auto} is the fraction of unsafe inputs allowed, and the benign-blocking rate FBauto\operatorname{FB}_{\rm auto} is the fraction of benign inputs blocked. A low miss rate can therefore come from allowing almost nothing.
Allowed-set risk instead measures the unsafe fraction among allowed inputs, with zero-denominator ratios undefined.




6.2. Policy Selection and Independent Confirmation



Symmetric policies link the thresholds through τL=1−τH\tau_{L}=1-\tau_{H}. We evaluate 101 pairs with τH\tau_{H} increasing from 0.5 to 1 in steps of 0.005. For each allowed miss rate ϵ∈{0.01,0.05,0.10}\epsilon\in\{0.01,0.05,0.10\}, we choose the pair with the highest automatic coverage on selection inputs, subject to Missauto≤ϵ\operatorname{Miss}_{\rm auto}\leq\epsilon and FBauto≤0.05\operatorname{FB}_{\rm auto}\leq 0.05. If coverage is tied, we prefer more automatic allowances, then the larger τH\tau_{H}. The search includes (τL,τH)=(0,1)(\tau_{L},\tau_{H})=(0,1), which sends every input for review and automates no decisions.



Selected thresholds remain fixed for confirmation and test, including policies that fail confirmation. A policy passes only when both error rates meet their limits. These checks use WAInjectBench and R-Judge, which provide the required partitions (Table 2).



Small samples and strict error limits.



A 1% miss limit requires zero misses among R-Judge’s 74 unsafe selection inputs and 49 unsafe confirmation inputs, because a single miss exceeds the limit in either set. WAInjectBench has 167 and 111, respectively, permitting one miss in each. With so few permitted errors, individual inputs can determine whether a policy passes, and larger samples are needed to estimate rare-error rates precisely.
The benign-blocking limit is similarly sensitive to individual errors. R-Judge confirmation permits at most two blocks among 44 benign inputs under its 5% limit, while test permits five among 111. Cluster-bootstrap intervals describe uncertainty from the sampled interaction records and attack sources.

6.4. Independent Allowance and Blocking Thresholds



We examine independent allow and block thresholds by removing the symmetry constraint: choosing a low allow threshold no longer forces a high block threshold. Each threshold has 101 evenly spaced candidates within τL∈[0,0.5]\tau_{L}\in[0,0.5] and τH∈[0.5,1]\tau_{H}\in[0.5,1], giving 101×101=10,201101\times 101=10{,}201 possible pairs. We separately maximize allowances within the miss limit and blocks within the benign-blocking limit. Because the score ranges do not overlap, this also maximizes total coverage. We use the same tie-breaking rules, then prefer the smaller τL\tau_{L} if a tie remains. We select thresholds on selection inputs and apply them unchanged to confirmation and test, comparing both policy types with original and recalibrated scores at all three miss limits.



Figure 9 compares symmetric (S) and independent (I) thresholds using original scores. Blue and yellow bars show the percentages of test inputs allowed and blocked. Circles mean both confirmation and test meet the 1% unsafe-miss and 5% benign-blocking limits. Triangles mean only test meets both limits. Crosses mean test exceeds at least one limit.



On R-Judge, independent thresholds raise Jev’s test coverage from 7.63% to 47.03% while meeting confirmation and test limits. Both policies allow just one input, while independent thresholds block 110. On WAInjectBench, coverage rises from zero to 6.70%, entirely through 108 blocks. Developers should report allowed and blocked fractions separately and compare observed error rates with both limits on independent labeled data.

6.6. Language-Model Judges as Potential Reviewers



An application can send uncertain inputs to a language-model judge for review. To assess models for this second-judge role, we compare their predictions with those of each System One model on the same inputs (Rao and Callison-Burch, 2026). We count an error as corrected when the judge predicts the benchmark label for an input the System One model misclassifies. A judge can correct the first model’s missed attack only when the review rule forwards that input, so selecting the reviewer also requires checking which cases the rule leaves unreviewed.



We compare four System One models with seven general judges on 1,612 shared WAInjectBench inputs, 236 R-Judge records, and 352 AgentHarm requests. Including task-compatible specialists gives 100 model pairs evaluated on the same complete test inputs within each task. For each class, a judge can correct or repeat the System One model’s errors, or make errors on inputs that model classified correctly. Figure 11 reports the fraction of the System One model’s errors corrected by each judge. Row counts give the original errors, and grey cells indicate no errors to correct. Table 16 also counts errors on inputs Jev classified correctly. GPT-4.1 identifies 10 of the 167 WAInjectBench attacks missed by Jev but misses 33 that Jev correctly flags. Its own miss count is therefore 190, showing that correcting some Jev errors need not reduce the total misses.

On AgentHarm, some judges detect previously missed harmful requests but falsely flag more benign ones. Kimi corrects all 14 Jev misses without introducing another miss, but repeats all 42 Jev false positives and adds 54. Across model and task pairs, every judge corrects over 80% of Laya’s and Decider’s AgentHarm misses, while no judge corrects even 10% of Nimble’s WAInjectBench misses. Choosing a review judge therefore requires checking the errors it corrects and introduces, along with which inputs reach it. Reviewing only uncertain inputs leaves confident mistakes unreviewed, even when another judge could detect them. Developers should apply the review rule to labeled validation inputs and count how many missed unsafe inputs it forwards, then compare both judges’ misses and benign false alarms on those inputs.





7. Discussion



7.1. Component Integration and Error Handling



Applications need explicit handling of input limits, invalid answers, missing scores, and network failures, sending inputs without usable scores for review. Deployment measurements also depend on the configuration: service routing, queueing, caching, and reasoning settings affect latency and API charges, while local backends and precision can affect scores.




7.2. Implications for Developing Agentic Software



Define the security task before selecting a model. Developers should specify the behavior to prevent, the legitimate work to preserve, and where the check affects the workflow. Checks on retrieved content, interactions, and user requests need different inputs and labels. For example, a request to summarize a dangerous command differs from a request to execute it, so the question, answer definitions, and available context should make the intended judgment explicit.



Choose models for the application’s requirements. Developers should compare candidates on representative labeled inputs at tolerable miss and false-alarm rates. The comparison should include task-compatible specialists alongside reusable typed components and general judges, taking context capacity and deployment resources into account. Because rankings and adaptation gains vary by task, candidates need to be evaluated with the question and input context the application will actually use.



Validate labels, probabilities, and policy actions separately. Developers should check classification errors across relevant input and attack groups, then assess whether probabilities reflect observed outcomes, particularly among inputs that would be allowed. Recalibration should be fitted on development inputs and cutoffs selected on selection inputs, with both frozen before independent checks. Policy validation should count unsafe inputs allowed, benign inputs blocked, and inputs sent for review, reporting allowed and blocked fractions separately because additional blocks do not enable more work to proceed. This staged validation supports component testing and monitoring in production ML engineering (Amershi et al., 2019; Breck et al., 2017).



Choose which inputs to review and which model reviews them. The second judge receives the inputs selected for review, which can differ substantially from the full workload. Developers should use labeled inputs to measure which missed unsafe inputs the rule forwards and which errors the judge corrects or introduces. If validation reveals confident mistakes that an uncertainty-based rule leaves unreviewed, developers should reconsider the question, context, model, or review rule, then test the revised combination.



Maintain validation as the software changes. Developers should record the model version, question, input construction, and cutoffs as one tested configuration and revalidate it whenever any part changes. Monitoring should include automatically handled inputs as well as reviewed ones, because errors in the former may never reach the second judge. Applications should define an explicit fallback for configurations that fail these checks.



Enforce permissions independently of model judgments. Access controls should restrict the resources an agent can use, while deterministic runtime checks enforce permitted operations (Debenedetti et al., 2026; Wang et al., 2026a). A safe prediction should not override these permissions, and the combined system should be evaluated by measuring successful attacks and completion of legitimate tasks.





8. Threats to Validity



Internal validity. Comparisons depend on prompts, answer-label order, context limits, reasoning settings, and services. Response sampling and output formats can affect scores. Recalibration uses only development data, and threshold selection uses only selection data, with no retuning on confirmation or test. Rare errors and few source clusters limit interval precision.
Construct validity. AgentHarm labels harmful requests as unsafe, while WAInjectBench labels attack-derived text as unsafe even without explicit instructions. The EI/no-EI, threshold-sensitivity, and cross-model error analyses are exploratory. Our finite grid restricts allowance thresholds to at most 0.5 and blocking thresholds to at least 0.5. Other policies may yield different trade-offs.
External validity. Public benchmarks may overlap training data, and unsafe-input proportions affect precision, AP, and calibration. Results may differ for adaptive attacks, other languages, and multimodal inputs. Hosted model revisions and service behavior can change between runs. Protection also depends on the agent, environment, guard placement, and handling of blocked requests, requiring validation in the target system.




9. Conclusion



Our evaluation shows that aggregate rankings and calibration metrics can conceal attacks confidently classified as safe, and that strong performance on one security task does not consistently transfer to another. Policies selected under strict error limits allow few test inputs automatically, while choosing the allow and block thresholds separately increases automation mainly by rejecting more inputs. Developers should therefore select models for each security task, verify policy error limits on independent labeled data, and test which missed unsafe inputs reach a second judge, measuring its misses and benign false alarms on the reviewed inputs.
