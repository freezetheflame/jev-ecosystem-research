## 2. Answers to the five questions

**Q1 — runnable attack optimization?** Yes, not just archives: `optimize_context` is a runnable particle/iteration optimizer with margin-based parent allocation, restarts, deterministic filters, checker gate, renderer and per-attempt logging. Interface: `optimize_context(item, target, proposer, checker, config=OptimizationConfig(...), target_option=None)`; CLI `context-opt optimize`; repo wrapper `scripts/jevout_pilot.py`. It targets the generic `DecisionTarget` protocol; the built-in `JevTarget` points at the official Jev endpoint (`api.typesafe.ai/v1/systemone`), with generic HTTP/callable adapters. There is **no** OpenLux-specific adapter in the engine — OpenLux appears only as a relay in `configs/*openlux*.json` and `security_bench` runs. Budget nuance: `optimize.py` has no explicit accepted-call counter; the paper's 64-cap is implicit (`particles × rounds`), while `independent.py` enforces explicit budgets.

**Q2 — semantic-validity checker / human-audit template?** Checker: yes — `checker.py::OpenAIContextChecker` + `prompts/checker.txt` + `CheckResult.accepted` + `deterministic_filters`. It is a single LLM judge, not independent validation; the repo's own two local flips were judged validity-risky (`docs/adversarial-robustness/jevout-40-results.md`; `data/jevout-pilot/experiment-audit.json`). Human audit: **no template or sheet exists.** Only requirements text: `docs/semantic-robustness/robustness-security-pilot-protocol.md` §2 (two independent reviewers, third arbiter, blind to model output/target) and `docs/model-evaluation/agent-security-experiment-protocol.md` (record reviewer, evidence, disagreement; AI may not be called human review). JevOut paper's annotation design is described in `data/JevOut/docs/results.md` but not shipped.

**Q3 — repeat/noise baseline?** Three partial pieces, no unified implementation: (a) JevOut `retest_context` — fresh 10× clean + 10× augmented, min 8 hits, cache bypass, revision/unit checks (used once, 1 case); (b) `security_bench` `repeats` in config → `runner.plan` schedules case×repeat×arm; `report.summarize` **pools** repeats into one confusion matrix (no per-repeat split); (c) `scripts/agentharm_repeat_metrics.py` keeps repeats separate (per-repeat metrics, item majority, Wilson CI) but its input schema is the AgentHarm pilot. Threshold/probability-drift analysis code exists in `rq1/ext-2026-11-13/derive_thresholds.py` but is written for RQ1 episode files, not repeats.

**Q4 — can `security_bench` inject a modified view for the same item without rewriting the pipeline?** **No, not as-is.** Static cases are built only by `datasets.load_static` (native adapters) or `dojo.prepare` (dynamic AgentDojo); `runner.plan` calls them; `case_id = digest([dataset_id, item_id])`, and `view`, `input_sha256` and `gold` are frozen in `cases.jsonl` then hash-verified by `verify_inputs`. There is no config/CLI field to supply external cases or variants; a perturbed view under the same `item_id` is a duplicate identity, and a new `item_id` requires new loader code. Closest precedent: `dojo.prepare` creates attacked cases with `condition: clean|attacked`, but only via fixed upstream non-adaptive attacks (`FIXED_ATTACKS`). Two viable paths: (i) use `framework/paired.py` — it consumes a normalized JSONL where each row's `state` is arbitrary text with its own `condition`/`label`, so a perturbed view is a new row with the same gold; constraints: ≥2 backends including one Jev + one openai_chat, legacy Mode A/B/C/D namespace, smoke/pilot only, `repeats=1`, 100-row default limit, per-backend metrics only; (ii) small extension to `security_bench` datasets/plan to register variant cases (code change + manifest/verification updates). Reusable now without either: multi-judge arms, budget/monitor, raw request+response retention (so probabilities can be re-parsed offline), and confusion-matrix reporting.

**Q5 — build from scratch (with nearest reuse anchor):**
1. **Judge-format attack generator/compiler**: JevOut generates sentences for one Jev question schema; need payload→each judge input format (json_risk system prompt, choice/noul/score, guard native templates) plus a `DecisionTarget` bridge over `security_bench` `Judge`.
2. **Per-item attack budget controller**: no joint accounting across proposer/checker/target or USD/time per variant; `security_bench` budgets are global.
3. **Variant registry/manifest**: variant_id ↔ base item/original_id ↔ gold/source ↔ attack family ↔ budget ↔ checker/audit status. Pieces exist only separately (`cases.jsonl` has case_id/input_sha256; `framework/paired` has original_id/condition; `report.template.md` `attack_manifest` is null).
4. **Human semantic-validity audit**: sampling design, blind sheet, adjudication, κ/agreement code (no template exists).
5. **Paired clean-vs-attacked analysis with same gold**: adapt `derive.py` McNemar + `bootstrap_cell` to variant pairing; add repeat-noise-adjusted deltas and gate-bypass (reuse `roc`/`tpr_at_fpr`); needs probability re-parse from `raw/*/response.body`.
6. **Same-payload multi-judge harness**: `security_bench` arms exist; missing payload compiler, identical policy/threshold freeze, and ASR/GBR metrics (paper 2610.17820 §4.3/§4.5).
7. **Gold/label dual-review workflow**: `gold_source`/`gold_validation` are required strings in `framework/paired.validate` but there is no reviewer tooling/storage.
8. **Robustness-specific frozen protocol**: `security_bench` already enforces a confirmatory manifest (status/frozen_at + exposure_audit, primary_metrics, sample_size_rationale, statistical_analysis, stopping_policy; `runner.execute`); the protocol content itself must be authored in this design dir.
